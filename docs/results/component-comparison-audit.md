# Component workload comparison audit

This source audit covers `crates/zgui-desktop/examples/component_workload.rs`, `comparisons/gpui/src/main.rs`, `comparisons/quickgui/src/main.rs`, and `comparisons/workload/src/lib.rs` as inspected on 2026-09-22. It describes the normalized component comparison, not the earlier low-level zgui adapter measurements. A benchmark series must identify its own frozen sources and executable hashes; this audit alone does not certify an executable.

The adapters describe the same 960 × 720 logical-pixel scene. The title starts at (20, 20), three 50 × 32 controls start at y = 55, status labels start at y = 62, the stream panel is (20, 110, 920, 160), and the clipped list is (20, 290, 920, 400). The stream inset is (8, 8); list labels use (8, 4). Colors agree: root `#10141c`, foreground `#e5edf7`, controls `#293b50`, panel/even rows `#192230`, odd rows `#1d2838`. All request DejaVu Sans, 14 px text with a 20 px line height; the 20 px heading uses a 28 px line height. Zgui derives these heights as `ceil(font_size * 1.4)` while the other adapters set them explicitly. This establishes matching requested geometry and typography, not pixel-identical rasterization across different text/rendering engines.

Each adapter consumes the shared deterministic workload: 100,000 logical rows of height 28, two overscan rows on each side, 14 px of scroll per delivered tick, and a bounded 8,192-byte stream. The displayed stream is the final 735 bytes split into at most seven 105-byte lines. Text generated by this workload is ASCII, so its byte slicing does not split UTF-8 characters. Row labels are shared as well. The normalized range starts at 0..17; interior positions mount 19 rows. Both the shared range calculation and zgui's virtual list use `floor(offset / 28) - 2` through `ceil((offset + 400) / 28) + 2`, clamped to the list bounds. The component example checks its mounted count against this shared range while scrolling.

The stream, scroll, combined, and idle modes use the same nominal 16,666,667 ns period. Timers advance one workload tick per delivered callback and reset the next deadline when updates overrun it, rather than accumulating an unlimited catch-up queue. The missed-deadline check occurs after the update in all three adapters. Timer initialization happens at different framework lifecycle points; warmup excludes startup from the main sample interval. Reported ticks count model updates, not displayed frames or GPU completion. Report active ticks alongside CPU/RSS and reject large throughput mismatches when interpreting comparisons. The sampler currently rejects zero active ticks, but does not itself enforce near-60-Hz throughput.

The implementation architecture deliberately differs: zgui mounts provider/component/slot descriptions once, updates tracked text signals, and retains keyed visible rows. GPUI and QuickGUI rebuild their element descriptions on view invalidation. Their list virtualization is implemented in the adapter using the same bounded shared range. This compares these application implementations and includes their framework overhead; it is not an isolated renderer benchmark or a claim about the fastest possible implementation in either framework. Zgui also tracks its mounted row count for its exit report.

Unattended measurements exercise streaming and automated scrolling. They do not measure button interactions, focus, accessibility clients, hover styling, wheel latency, IME, blur, or edge fades. The buttons implement the same bounded append, repeated row write, and done-state operations, but framework-specific default hover/focus presentation and event behavior are outside the measured workload. Resizing is disabled in the zgui example; the reference windows are resizable, and comparisons must leave all windows at their initial dimensions. Font fallback and rasterization can differ despite the same requested family. Linux Xvfb/llvmpipe CPU includes software rendering and cannot establish hardware GPU performance, macOS performance, presentation latency, or a universal CPU/memory advantage.

## Earlier component release smoke provenance

`component-release-smoke/source.tar.gz` contains 60 files; every archived file's SHA-256 was checked against `component-release-smoke/metadata.json` without a mismatch. At audit time, the release component executable still matched that smoke's recorded executable hash. The shared workload and component example have since changed for normalization, so these are pre-normalization smoke artifacts and must not be reused as the normalized series' source evidence.

That smoke completed all four five-second modes successfully: idle reported zero ticks, and each active mode reported 299. Mounted counts were 17 for idle/stream and 19 for scroll/combined. These records prove successful execution of the preserved smoke binary with bounded final row counts; they do not prove a repeated comparison against freshly rebuilt reference adapters. Preserve them as separate historical evidence when recording the new series.
