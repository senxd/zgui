# Why a frozen candidate anchor is not a complete framework remedy

The current desktop host reads the retained editor caret rectangle in `crates/zgui-desktop/src/application.rs` and forwards it after rendering. `crates/zgui/src/widgets.rs` computes that caret from shaped display text and the preedit cursor, then scrolls the editor to reveal it. The test `native_ime_caret_follows_selection_and_preedit_has_underline` verifies that the visible caret follows composition. Editor geometry remains meaningful for wrapping, bidirectional text, and changing preedit selections.

Wayland text-input-v3 defines the candidate rectangle as an area around the cursor and uses it to position suggestions near edited text without obstruction. See the [official protocol source](https://cgit.freedesktop.org/wayland/wayland-protocols/tree/unstable/text-input/text-input-unstable-v3.xml); the locally installed protocol is under `/usr/share/wayland-protocols/unstable/text-input/text-input-unstable-v3.xml`.

A separately calculated composition-start anchor could be a deliberate candidate-placement policy without moving the visible caret or modifying committed text. It would need a separate geometry API based on the composition insertion range, recomputation from current shaped layout, clipping/scroll handling, and lifecycle invalidation. Capturing a screen coordinate and freezing it is insufficient: wrapping, long preedit autoscroll, viewport movement, DPI/font changes, and window resizing can move the relevant text or hide the start entirely. A legitimate anchor must update for those changes, and every such update can still advance the input-method serial. A composition-range rectangle also changes as text grows and likewise does not remove the race.

Consequently, adopting a stable anchor solely to eliminate this failure would trade a general protocol issue for candidate-position errors and only suppress one trigger. The standalone winit reproduction already proves the failure does not require zgui's rendering path. Moving cursor synchronization before rendering or introducing delays is also only a timing hypothesis. Existing X11 baseline positioning and macOS rectangle behavior should remain untouched.

The more direct bounded experiment is a private Fcitx frontend refresh of current nonempty preedit after ordinary input-method done, at the new serial. The archived patch and actual recovery trace test that hypothesis. This does not replay committed text/deletions, and its limited verification is not a claim of a complete upstream protocol repair.
